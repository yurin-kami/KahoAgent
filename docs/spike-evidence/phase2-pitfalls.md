# Phase 2 踩坑记录

三个坑。与 Phase 1 不同的是，这些**不会报错、不会挂测试** ——
它们只让指标悄悄变差，或者在故障时悄悄放大损失。
只有靠「先量化再下结论」的评估流程才能揪出来。

---

## 坑 1：RRF 的一致性加分会在两路质量悬殊时反噬

### 现象

混合检索的 MRR **低于**单独用 BM25：

```
Method               Recall@5    MRR
bm25-only            0.357       0.720
hybrid-rrf           0.348       0.698   ← 融合之后反而更差
```

按「融合取长补短」的直觉，这说不通。

### 排查过程

**第一步：分清「找不到」还是「排不对」。**

检索失败分两种，处理方式完全不同：

- 召回失败：相关块压根不在候选池 → 后面做什么都白搭
- 排序失败：在池子里但没排到前面 → 精排能救

看 recall@50（只看有没有，不看顺序）：

```
vector recall@50 = 0.707
bm25   recall@50 = 0.740
```

两路接近，**都能找到**，问题纯粹在排序。
这一步直接排除了「向量索引建错」「分词有问题」一整类猜想 ——
省掉了去读 RRF 代码找 bug 的时间，因为那里根本没有 bug。

**第二步：定位到机制本身。**

RRF 只用排名不用分数（这是它的优点：绕开了「余弦相似度 0.82 和
BM25 分数 12.7 怎么比」这个没有正确答案的问题），
但代价是**丢掉了强度信息**：

| 情况 | 得分 |
|---|---|
| 被 BM25 排第 1，但不在向量的 50 条里 | 1/61 = **0.0164** |
| 被两路都排第 10 | 1/70 + 1/70 = **0.0286** |

**单路强命中输给了双路平庸。**

RRF 隐含的假设是「两路都认可 = 更可信」。这个假设在两路质量相当时成立，
在质量悬殊时就变成噪声投票 —— 弱的那一路有权把强的那一路的第一名踢出前五。

逐查询验证（`scripts/eval/diagnose.go`）：77 条里 11 条 hybrid 输给 bm25，
其中 8 条（73%）是向量路 RR 低于 BM25。最极端的三条：

| 查询 | bm25 | hybrid | vector |
|---|---|---|---|
| 热点key突然失效导致数据库压力暴增怎么办 | 1.000 | 0.000 | 0.000 |
| 大量缓存同时过期怎么处理 | 1.000 | 0.000 | 0.000 |
| MySQL 里读到别的事务没提交的数据是什么问题 | 1.000 | 0.250 | 0.000 |

全是 `confusable` 类。向量路 RR = 0.000 表示前五一条都不对，
而 BM25 稳稳第一，融合后变成 0.000 —— **融合把唯一正确的信号抹掉了**。

原因不难理解：「缓存击穿」和「缓存雪崩」在向量空间里几乎重叠，
embedding 分不开这种**共享大部分语义、仅靠一个词区分**的概念。
BM25 靠字面匹配，「击穿」就是「击穿」，天然不会混。

**第三步：加权 RRF 为什么不是解法。**

最自然的想法是给两路加权重。扫描 9 组（`scripts/eval/weight_sweep.go`）：

| vector:bm25 | MRR | confusable | semantic | keyword |
|---|---|---|---|---|
| 0.0:1.0 | **0.720** | **0.625** | 0.560 | 0.855 |
| 0.5:1.0 | 0.714 | 0.508 | 0.559 | 0.868 |
| 0.7:1.0 | 0.705 | 0.456 | 0.539 | **0.876** |
| 1.0:1.0（当前） | 0.698 | 0.406 | 0.559 | 0.858 |
| 1.0:0.5 | 0.707 | 0.344 | 0.632 | 0.834 |
| 1.0:0.3 | 0.707 | 0.344 | **0.638** | 0.829 |
| 1.0:0.0 | 0.656 | 0.250 | 0.540 | 0.821 |

只看总 MRR 会得出「加权无效，纯 BM25 最好」的结论。但看后三列：

- `confusable` 最优在 **0.0:1.0**
- `semantic` 最优在 **1.0:0.3**
- `keyword` 最优在 **0.7:1.0**

**三类的最优权重互相矛盾，且分布在区间两端。**

总 MRR 在 0.0:1.0 取最大只是因为 keyword 类占 40/77，
样本量最大的一类主导了平均值 —— 这个「最优」不是任何一类的最优解。
而查询进来时并不知道它属于哪一类，所以**静态全局权重是死路**。

（先分类再选权重当然可以，但那等于在检索前又加一个需要评估、
会出错、有延迟的分类器 —— 复杂度换来的收益还不如直接上精排。）

### 结论

不改 RRF，交给精排。recall@50 已有 0.70+，正确答案本就在候选池里，
缺的是**新的判据** —— 融合阶段（无论怎么加权）都只有排名可用，
而精排能让 LLM 直接读内容。实测 MRR 0.698 → 0.802，
`confusable` 0.406 → 0.629。

**RRF 的职责不是「排对」，而是把两路候选合并成有序池子交给精排。**
用「融合后的 MRR」要求 RRF 达到精排的效果，本身就是错配的期待。

### 教训

- **先分层定位，再看实现**。一个 recall@50 就把问题锁死在排序层。
- **分类型指标比总分有用得多**。当一个平均值掩盖了互相矛盾的子群体时，
  优化这个平均值没有意义。
- **RRF 的 k=60 是有前提的**。Cormack 那篇论文是在两个质量相当的
  检索系统上调出来的，照搬前要确认前提成立。

## 坑 2：兜底路径与主路径的量纲不一致

### 现象

没有现象 —— 这正是它的危险之处。不报错、不挂测试、不影响正常流程，
只在 LLM 打分失败时悄悄把一个可能相关的块踢到最后。

### 根因

精排给每块打分，成功时**归一化到 0-1**：

```go
return float32(v / maxScore), true   // 10 分 → 1.0
```

而打分失败时保留原有的 RRF 分数，注释写得很清楚：

```go
// 单块打分失败时保留原 RRF 分数，不让整次精排失败。
// 保留原分数而非置 0，是为了让它仍能参与排序 ——
// 置 0 会把一个可能相关的块直接踢到最后。
```

意图完全正确，实现完全错误：**RRF 分数在 0.016 量级**。

0.0164 比任何打过分的块都低 —— 连被判为「完全不相关」（0 分 → 0.0）
的块……好吧，那个更低，但只要有任何一块得了 1 分（0.1），
失败的块就垫底了。**兜底逻辑精确地做到了它注释里说要避免的事。**

当时的测试也没拦住，因为它断言的是「分数等于原值」——
而它确实等于原值：

```go
if got[0].Score != original {   // 通过，但通过得毫无意义
```

测试忠实地固化了错误的行为。

### 修复

取**成功块分数的中位数**作为兜底 ——「未知 ≈ 平均水平」：

```go
fallback := float32(median(succeeded))
for i := range scored {
    if !ok[i] {
        scored[i].Score = fallback
    }
}
```

再由 `sort.SliceStable` 在并列时保持 RRF 原序，
于是多个失败块之间仍按 RRF 的偏好排列。

顺带改了另一处：**全部块都打分失败时返回 error**，而非静默返回 RRF 顺序。
调用方 `HybridRetriever` 收到 error 会记 warn 并降级用 RRF 结果 ——
用户看到的结果一模一样，但故障从「无声」变成了「有日志」。
一次彻底的 LLM 故障不该伪装成一次成功的精排。

### 教训

**兜底路径要和主路径量纲一致。** 这类 bug 不报错、不挂测试，
只在故障时悄悄放大损失 —— 而故障时正是你最不希望系统再多坏一点的时候。

顺带一条：**测试断言要写「应该怎样」，而不是「现在怎样」**。
原测试断言「分数等于原值」，把实现细节固化成了契约；
新测试断言「不能垫底」，描述的才是真正要保证的性质。

## 坑 3：`temperature=0` 不等于可复现

### 现象

精排固定了 `temperature=0`，连续三次运行仍得到不同结果：

| 运行 | MRR | confusable |
|---|---|---|
| 第 1 次 | 0.800 | 0.546 |
| 第 2 次 | 0.810 | 0.629 |
| 第 3 次 | 0.802 | 0.629 |

同期 `vector-only` / `bm25-only` / `hybrid-rrf` 三行**逐位相同**
（0.656 / 0.720 / 0.698），可见波动来自模型侧而非评估流程。

### 根因

`temperature=0` 只保证采样时取最大概率的 token，
**不保证 logits 本身逐位一致**。服务端的批处理规模、
GPU 并行归约顺序都会影响浮点累加，进而在两个概率接近的 token 之间
翻转结果。打分 prompt 输出的是「7」还是「8」，本就常处于这种边界。

### 应对

不追求消除（做不到），而是**披露**：报告里写明精排行应理解为「约 0.80」，
并注明小于约 0.01 的差异不具备说服力。

这条直接影响怎么用这张表：如果之后有人改了 prompt 看到 MRR 从
0.802 涨到 0.808 就宣布优化成功，那是在读噪声。

### 教训

**在用一个指标做 A/B 判断之前，先测它的重复性。**
不知道噪声底噪有多大，就无法判断一个差异是不是真的。
测法很简单：同样的代码跑三次。
