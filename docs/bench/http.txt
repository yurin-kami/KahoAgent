## 这些数字真正说明什么

**瓶颈不在 KahoAgent，在上游 LLM 的账号并发配额。**

依据有三条，缺一不可：

1. 三档速率下**完成延迟几乎不变**（7.0s / 7.6s / 7.2s）。若是本服务过载，
   排队会让延迟随速率显著上升 —— 它没有。
2. 20 req/s 时吞吐**卡在 10 req/s 不再增长**，多出来的全部失败。
3. 服务端日志里 187 次失败**全部**是同一个错误：

   ```
   HTTP 429: {"error":{"message":"Too many concurrent requests.",
              "type":"Throttling.Concurrency","code":"Throttling.Concurrency"}}
   ```

   这是 DashScope 返回的，不是本服务返回的。

所以「QPS ≈ 10」是**当前 DashScope 账号配额下的**上限，换个配额更高的
账号或换自建模型，这个数字就会变 —— 它不是本项目的架构容量。

顺带说明：完成延迟 P50 7 秒也不是本服务慢，那是模型生成几百字所需的
时间。真正反映服务响应能力的是**首字延迟 P50 约 430ms**，
且它在三档速率下都稳定 —— 说明流式链路本身没有被压力影响。

## 失败时的行为

187 次失败全部以 SSE `error` 事件返回给客户端，服务未 panic、
未拒绝新连接、未泄漏 goroutine（压测结束后 /metrics 的
kaho_active_sessions 归零）。这是 Phase 3「工具/上游报错时优雅降级」
在真实过载下的验证。
