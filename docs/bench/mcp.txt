## 读数说明（不看这段容易误读）

**P50 9ms 不代表检索只要 9ms。**

压测脚本循环使用 5 个查询，300 次调用里绝大多数命中了 Redis 缓存 ——
9ms 是**缓存命中**的延迟。真实的未命中延迟看 P95/P99（2.5s / 4.1s），
那才包含向量化 + Milvus + PostgreSQL + LLM 精排的完整链路。

两个数字都有意义，但要分清：
- P50 9ms  → 缓存工作正常（Phase 2 实测缓存带来 273 倍差距，此处印证）
- P99 4.1s → 冷查询 + Guard 排队的最坏情况

**工具数显示 1，因为压测时没配 CLOUDKAHO_TOKEN。**
没有 token 时文件类工具会被**刻意跳过注册**（见 internal/app/app.go）——
注册一个必然失败的工具，只会让模型反复重试撞上 MaxIterations。
需要 4 个工具的验证见 cmd/mcp/e2e_test.go 的 TestMCPE2E_ListsFourTools。

## 与 HTTP 路径的对比

| | HTTP /api/chat | MCP rag_query |
|---|---|---|
| 吞吐 | ~10 req/s（受 DashScope 配额限制） | 69.7 call/s |
| 瓶颈 | 上游 LLM 生成 + 账号并发配额 | 无（未触及） |

差距的原因：MCP 的 rag_query **只做检索，不生成**。生成那 7 秒和
DashScope 的并发配额都不在这条路径上。这也说明把工具经 MCP 暴露出去
是有额外价值的 —— 客户端（Claude Desktop）自己承担生成，
本服务只提供检索能力，吞吐高一个数量级。
